# ADR-001: Modular Monolith With Vertical Slices

**Status:** Accepted  
**Date:** 2026-09-13  
**Author:** Apurba Biswas  
**Quest/Week:** Week 1, "Hello, CareCommerce"

---

## Context

**Team:** Single developer.

**Domain:** Three features today — clinics, supplies, appointments. A clinic orders supplies from
the catalogue. An appointment is a supply-side visit to the clinic (delivery slot, equipment
service visit, or rep consultation), usually linked to the order that caused it. So appointments
depend on both clinics and supplies.

**Timeline:** Notifications is extracted as a separate service in Week 10. Q2 splits the system
into three services. Today's structure must make those extractions cheap.

**Constraints:** One Docker image that runs locally; Azure deployment later. No PHI inside the
system boundary (see C4 context).

**What is unknown:** Real load, and where the domain boundaries will finally settle.

---

## Decision

We will build CareCommerce as a single deployable ASP.NET Core API, organised as a modular
monolith with vertical slices.

Rules:
1. Each feature owns its code in `feature/<name>/` — endpoints, models and storage together.
2. A feature may call another feature only through that feature's public contract (an interface
   or public service). It never uses another feature's internal classes, such as its store, directly.
3. Only cross-cutting concerns (error handling, CORS, health, later auth and audit) are shared,
   and they are wired in `Program.cs`.

---

## Options Considered

### Option A: Traditional layered monolith
- **Pros:** Easy to develop. Code is easy to reuse across layers. Low learning curve, friendly for juniors.
- **Cons:** Features are spread across every layer, so extracting one later means untangling all
  of them — high effort. One deployable unit; a failure can affect the whole server.

### Option B: Modular monolith with vertical slices
- **Pros:** Still one deployable unit, cheap to run. Features are isolated in their own folders,
  so a change in one has fewer side effects on others. Extraction to a service costs less, as long
  as the module rules are followed.
- **Cons:** Still one process — if one feature crashes the server, all features suffer. Some
  duplication between features is accepted. Calling another feature needs a public contract,
  which is more work than a direct class call.

### Option C: Microservices
- **Pros:** Separate service per module. Failures are isolated per service. Each service can be
  scaled and deployed independently.
- **Cons:** Expensive for a small to medium application. More effort to develop, deploy, monitor
  and debug (network calls, distributed failures, multiple containers locally). Domain boundaries
  are still unknown — a wrong boundary between services is much more expensive to fix than a
  wrong folder boundary.

---

## Consequences

### Positive
- Less expensive and less effort to build and manage.
- One single deployable unit — one image, one pipeline.
- Moving a feature to its own service later is cheaper, **if** the module rules are followed.

### Negative / Trade-offs
- Some code duplication between features.
- A feature that needs another feature's data must go through its public contract, not reach
  into its classes directly.
- If one feature brings the process down, the whole server goes down.
- Features cannot be scaled separately.

### Risks
- **Modules quietly depend on each other** until extraction becomes a rewrite.
  *Detect:* any `using CareCommerece.feature.<other>` that touches a non-public class.
- **Single developer** — nobody else enforces the module rules.
  *Detect:* review cross-feature references before each boss battle.
- **In-memory state** — `ClinicStore` is a singleton, so only one instance can run.
  *Detect:* must be removed before scaling out or deploying more than one replica.

**Revisit this ADR when:** Week 10 Notifications extraction starts, or one feature needs to scale
or deploy independently of the others.

---

## Compliance / Domain Notes (Healthcare / E-commerce / Enterprise)

- **Healthcare (HIPAA):** No PHI in scope — patients are out entirely and appointments are
  supply-side visits, so this decision has low HIPAA impact. Patient scheduling, if ever added,
  is a separate bounded context and a new ADR. Audit middleware (Week 3) sits once in the shared
  pipeline and covers every module.
- **E-commerce (peaks, payments):** Ordering peaks (month-end budgets, flu-season vaccines) cannot
  be scaled on their own — the whole app scales, which requires removing in-memory state first.
  Payments (Stripe, Q2) get their own module so they are the first candidate for extraction.
- **Enterprise (SSO, audit):** One app means one auth setup (Entra External ID / Auth0, Week 7)
  and one place for the `CanApproveOrder` policy. One audit trail, no cross-service log correlation.
